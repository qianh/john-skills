## 1. 目标

### 1.1 四个目标怎样算达成

| 目标 | 怎样算达成 | 主要机制 |
|---|---|---|
| 交付质量 | 结论为「完成」时，每条完成标准都有证据；对最终代码有一份有效审查且没有未关闭的 P1；审查者和所有代码作者不同家族 | 第 3、4、5 节 |
| 物尽其用（每个模型放在它最该在的位置） | 每个位置由配置声明的能力担任；替换只在这个位置的候选链里进行，替补按自己的思考程度运行；能力和本机 ID 解耦，换机器只改本机路由 | 第 8 节 |
| 调度丝滑 | 正常路径下主会话只运行一条命令、读一份汇总；需要主会话介入时，汇总给出唯一、明确的下一步；中断后可以接着跑；不需要主会话转述错误 | 第 3、9 节 |
| 不浪费 token | 小活不外派；已知不可用的路由不重复试；便宜的检查放在贵的检查前面；账本按次记增量，未知金额不当成零；收益用对比实测证明 | 第 9.4、10 节 |

### 1.2 不做的事

- 不重写主流程；不加难度分档、升级梯子或新的调度层（重设计方案第 2 节）。
- 不做按单次请求的模型网关。
- 不在主会话里逐步指挥 worker。
- 不为了「每个模型都有活」硬塞位置。没有合适位置的能力就不路由。
- 不承诺绝对不超支、绝对零泄露。承诺范围以实测过的边界为准（不变量 I3、I5）。

### 1.3 现状

主路径已经跑通：探索 → 方案 → 执行 → 审查 → 修复 → 脚本复核，`bun test` 33 项通过。几轮独立审查加上本机核对，共确认 36 个问题（附录 A）。另外，本机 codex 已经从重设计方案记录的 0.42.0 升到 0.164.0，`args.ts` 里的版本说明已经过时。

## 2. 不变量

每条写明：内容、依据、违反时怎么处理。第 3–10 节的机制都要能追溯到这里。

### I1 完成必须有证据

结论为「完成」，当且仅当以下条件同时满足：

1. 方案有效（第 4.1 节），并且至少有一条完成标准。
2. 每条「命令」类标准都在**最终快照**（第 7 节）上由脚本运行通过；每条「核验」类标准都有主会话的核验记录。
3. **最终快照**有一份有效审查（第 4.2 节），P1 为空。
4. 审查者和本次所有代码作者不同家族（I2）。
5. 没有未处理的安全标记：敏感文件被改动、越界改动没有被审查接受、暂存区或 HEAD 被改动、依赖文件改动没有授权。

验收和审查都要记录它们针对的快照 id。三个 id（验收、审查、最终）必须相同，才算对同一份代码给出了证据。任何一条不满足，结论只能是「待验证」「卡住」「交给主会话」「中断」之一（第 3.2 节）。

依据：用户准则「成功不可跨层外推」「完成前检查实际产物」；重设计方案「不采信模型自报」。

### I2 审查真实且独立

- 只采信通过校验的审查结论。格式或内容不合法就是无效，不能当成「没有问题」。
- 每次实际选择审查者时，都对照本次所有代码作者的家族。作者包括首次执行、修复、接手的模型，以及代做过执行或修复的主会话。同家族的候选跳过。
- 家族未知的作者，按「和所有家族都冲突」处理。
- 找不到独立的审查者，就交给主会话代审。主会话和作者同家族时，结论最多是「待验证（独立性不足）」。

### I3 发出去和留下来的内容，都经过同一套安全规则

- 覆盖范围：发给任何模型的所有提示词、写进运行目录的所有文件、输出到 stdout 的汇总。
- 已知的敏感路径在**读取之前**就排除。模型回传的文本和命令输出，在落盘和转发之前做内容扫描。
- worker 自己去读文件的行为，靠外壳实测过的读取限制来约束（第 6.4 节）。默认不使用没有读取限制的外壳。用户逐个外壳显式放行的例外，写进汇总。事后提醒挡不住已经发生的读取，所以不能代替默认限制。
- 环境变量也算外发内容：验收命令和 worker 只拿到白名单里的变量（第 6.6 节）。

依据：用户准则 10「敏感信息零暴露」。

### I4 不动、不混淆用户已有的修改

- orchestrator 不对用户的文件做 stash、reset、checkout、add，也不修改用户的暂存区。
- 审查、汇总、修复都只针对「基线 → 当前」的增量。
- 开跑前已有用户修改、又被本次运行改动的文件，单独标出来。

依据：用户准则 5「保护用户修改」。

### I5 权限承诺以实测过的边界为准

- 强制边界分五层：文件写入范围、Git 元数据、网络、凭证（环境变量和凭证文件）、读取限制（第 6.1 节）。在这之上还有用户授权（第 6.3 节，I6）。
- 承担执行的外壳，每一层都必须有实测过的强制手段。做不到的层，默认不让它执行；用户在配置里显式放行时可以执行，汇总里要标出来。
- 脚本自己运行的验收命令，也在这些边界内运行。
- 某一层被用户放开后（例如联网），汇总不再声称这一层有物理隔离，而是写明还剩哪些约束。
- 不给任何 CLI 加 bypass、yolo、always-approve 一类参数。

### I6 授权只来自用户

- 新依赖、联网、发布、部署、推送、删除数据、改生产配置这类动作，只能由用户的明确授权放行（`--allow`，第 6.3 节）。
- 方案、审查、执行模型的输出都不构成授权。识别危险命令只是辅助手段，没识别出来不等于已经授权。
- 授权按类别分别给出，类别之间互不包含。联网授权不等于发布、推送、部署授权（第 6.3 节）。

依据：用户准则 9「危险操作需授权」、11「新依赖需确认」。

### I7 位置不错配，替换要可见

- 每个位置的候选和思考程度都由配置声明。替换只在这个位置的候选链里进行，替补按自己的思考程度运行。
- 配置缺失或不完整时，停下来说明原因，不静默换成别的配置。
- 每次替换和跳过都写进汇总：哪个位置、原定谁、实际是谁、原因。

### I8 账本诚实

- 每次调用记录这一次的增量。金额分三类：CLI 报价、按价格估算、未知。未知不当成零。
- 失败、超时、重试的调用同样适用：能拿到用量就记，拿不到就是未知；只有能证明请求没有发出或没有计费时，才记零（第 10.1 节）。
- 对照用的数字要如实命名，例如「本次 token 按 opus 单价重算」。

### I9 可恢复，不重复副作用

- 每个步骤开始和结束时都落盘。同一个运行，同一时刻只有一个进程在推进；同一个工作区，同一时刻只有一个会改代码的运行。
- 恢复时，只读步骤可以重跑；改代码的步骤不盲目重放，而是从当前工作区状态续做。
- 主进程不在了，不等于它启动的 worker 也停了。恢复前要确认旧 worker 已经停止，确认不了就不推进（第 9.2 节）。

### I10 主会话上下文干净

- stdout 只输出汇总，不超过 30 行。worker 的原文只落文件，主会话按风险抽查。

## 3. 修订后的流程

### 3.1 流程

~~~
orch run "<目标>" [--allow 类别,...] [--exec 能力名] [--plan-only] [--budget 美元] [--max-calls 次数] [--max-minutes 分钟]
 0 加载并校验配置。出错即停，0 token
 1 预检：外壳安装和登录状态、不可用缓存、隔离和读取准入、git 状态。0 token
 2 加锁，记录基线快照。0 token
 3 探索：廉价只读模型 → explore.md（经过内容扫描）
 4 方案：JSON 契约 → plan.json，脚本渲染出 plan.md
     格式无效 → 在同一会话里要求修正一次 → 仍无效 → 交给主会话
     需要授权但没有授权，或者带了 --plan-only → 交给主会话（方案闸门）
 5 执行：一个会话做完
 6 修复循环，验收失败和 P1 共用 max_rounds 轮
     a 脚本验收（只跑「命令」类标准）
          失败 → 交回执行会话修复，消耗一轮 → 回到 a
     b 审查：JSON 契约，针对当前快照
          无效 → 在同一会话里要求修正一次 → 仍无效 → 卡住（审查无效）
          有 P1 → 交回执行会话修复，消耗一轮 → 回到 a
          没有 P1 → 进入 7
     轮次用完 → 卡住
 7 「核验」类标准：有 → 交给主会话核验；没有 → 跳过
 8 收尾：按 I1 判定结论，写汇总，解锁
~~~

和现状相比的关键变化：

- **验收放在审查前面。** 脚本验收不花 token，审查用的是最贵的模型和最高思考程度。代码还跑不通时，不浪费一次审查。
- **验收失败也会交回执行会话修**，和 P1 共用同一个轮次上限，不另给额度，也不需要主会话转述错误。
- 循环结束时，最后一次验收和最后一次审查针对的是同一个快照，满足 I1。

### 3.2 结论类型

| 结论 | 含义 | 退出码 | 主会话下一步 |
|---|---|---|---|
| 完成 | I1 全部满足 | 0 | 汇报 |
| 卡住 | 轮次用完仍有 P1 或验收失败；审查无效；核验未通过且没有剩余轮次 | 1 | 交给用户决定 |
| 用法或配置错误 | 参数错误、配置缺失或不合法 | 2 | 修正后重跑 |
| 交给主会话 | 某一步没有可用模型；方案闸门；「核验」类标准待确认；达到预算、调用次数或时长上限 | 3 | 只做指定的那一步，然后 continue |
| 中断 | 进程被杀，或基础设施出错 | 4 | continue |
| 待验证 | 改动已经做完，但还有证据缺口：独立性不足、有安全标记、验收命令没能自动运行（所在平台没有沙箱，或者命令被安全规则挡住） | 5 | 按汇总列出的缺口核验，或者交给用户 |

### 3.3 「交给主会话」协议

- 汇总里写清楚：哪一步、原因、要写的文件及其格式（给出 JSON schema 的路径）、做完后要运行的命令。
- 主会话做完后运行 `orch.ts continue --run <目录> --by <能力名>`。`--by` 填主会话自己的能力名（例如 `sonnet-5.5`），用于家族检查；缺了 `--by` 直接报用法错误。
- 主会话只做这一步，不顺手把后面的阶段做掉。
- continue 时，脚本先给工作区拍一次快照，和记录比对。
  - 不是改代码的交接（例如核验），工作区却变了：把 `--by` 记为代码作者，回到第 6a 步重新验收和审查。
  - 运行期间用户手动改了文件，也会被计入增量。所以 SKILL.md 要提醒主会话告诉用户：运行期间不要手动改工作区。

| 交接类型 | 主会话要做的事 |
|---|---|
| plan | 按 schema 写 `plan.json` |
| exec / fix | 按方案或 P1 改代码，不 commit |
| review | 只读审查，写 `review-N.json` |
| check | 逐条核验「核验」类标准，写 `checks.json` |
| permission | 把需要授权的动作告诉用户。用户同意，就 `continue ... --allow 类别`；不同意，就结束，只保留方案 |
| budget | 告诉用户已知花费、未报价的调用次数和已用时长。用户同意追加，就带上新的 `--budget`、`--max-calls` 或 `--max-minutes` 运行 continue |

## 4. 交接契约

### 4.1 方案：`plan.json`

字段：

| 字段 | 类型 | 规则 |
|---|---|---|
| `exec_type` | 枚举 | `mechanical`、`standard`、`hard` 之一 |
| `criteria` | 数组，至少 1 条 | 每条有 `id`（不能重复）、`kind`（`command` 或 `check`）、`text`。`command` 类必须带 `commands`（至少 1 条，每条一行），`check` 类不能带 |
| `allowed_paths` | glob 数组，至少 1 条 | 允许修改的范围，用 `Bun.Glob` 匹配（内置，不引入新依赖） |
| `needs_permission` | 数组 | 每条有 `category`（`deps`、`network`、`publish`、`deploy`、`push`、`data`、`prod-config`、`other`）和 `reason` |
| `steps` | 字符串数组，至少 1 条 | 实施步骤 |
| `context` | 数组 | 每条有 `ref`（`路径:行号`）和 `note`，让执行者不用重新翻仓库 |

示例（已用 bun 1.3.4 解析通过）：

~~~json
{
  "exec_type": "standard",
  "criteria": [
    { "id": "C1", "kind": "command", "text": "单元测试通过", "commands": ["rtk bun test skills/orchestrate"] },
    { "id": "C2", "kind": "check", "text": "README 新增「本机适配」一节，说明 init 两步流程" }
  ],
  "allowed_paths": ["skills/orchestrate/scripts/**", "README.md"],
  "needs_permission": [],
  "steps": ["……"],
  "context": [{ "ref": "skills/orchestrate/scripts/flow.ts:90", "note": "parsePlan 在这里" }]
}
~~~

怎么拿到：

- claude 和 grok 传 `--json-schema`，codex 传 `--output-schema`（本机 `--help` 已确认三个参数都存在）。结构化结果出现在各家 JSON 输出的哪个字段，待实测。
- pi 没有这个参数。提示词要求回复里**恰好一个** ```` ```json ```` 代码块；没有或有多个，都判为无效。
- 不管从哪条路拿到，都走同一个校验函数。CLI 自己做了 schema 校验，脚本也不跳过。

判为无效的情况（任意一条成立）：

- 缺字段、类型不对、枚举值不合法；
- `criteria` 为空、`id` 重复、`command` 类没有命令、`check` 类带了命令；
- 顶层出现重复的键。`JSON.parse` 遇到重复键会静默保留最后一个，所以要在原文上检查顶层的键有没有重复；
- 命令里含换行。

因为「完成标准至少 1 条」，planner 没法靠「验收写无」绕过复核。全是「核验」类时，会走第 7 步交给主会话核验。

### 4.2 审查：`review-N.json`

| 字段 | 规则 |
|---|---|
| `p1` / `p2` | 都必须出现。空数组表示明确没有问题，不再有「写了无又列了问题」的歧义 |
| 每条发现 | `ref`（路径，尽量带行号）和 `issue`，都不能为空 |
| `criteria` | 方案里每条「核验」类标准的 `id` 恰好出现一次，带 `verdict`（`pass`、`fail`、`unknown`）和 `note`。`fail` 自动按 P1 处理 |
| `out_of_scope` | 脚本提供的每个越界改动路径都要出现一次，带 `accept` 和 `reason`。`accept: false` 自动按 P1 处理 |
| `reviewed_tree` | 原样回填提示词里给出的快照 id。不一致就判为无效，防止审错了版本 |

示例（已解析通过）：

~~~json
{
  "p1": [{ "ref": "skills/orchestrate/scripts/flow.ts:95", "issue": "验收命令仍有全文兜底" }],
  "p2": [],
  "criteria": [{ "id": "C2", "verdict": "pass", "note": "已核对 README 第 40 行起" }],
  "out_of_scope": [],
  "reviewed_tree": "<脚本给出的快照 id>"
}
~~~

顶层键重复、缺字段、`criteria` 漏了某条或者重复，都判为无效。格式修正只允许一次：在同一会话里把校验错误列给对方，请它重写。

### 4.3 完成标准和证据

- **命令类**：由脚本在沙箱里运行（第 6.5 节），记录快照 id、退出码和经过扫描的输出尾部。
- **核验类**：主会话在 check 交接里逐条确认，写进 `checks.json`（`id`、`verdict`、`evidence`）。审查者对这些标准的判断只作参考。
  - 主会话判定 `fail` 的条目按 P1 处理。还有剩余轮次时，continue 会交回执行会话修复；没有剩余轮次，就是「卡住」。

### 4.4 提示词改动

| 提示词 | 改动 |
|---|---|
| 执行 | 删掉「除非方案明确写了」。只做已授权的动作；需要未授权的动作时停下来，在回复里说明。列出开跑前已有修改的文件，要求不撤销、不改写，除非方案明确要改这些文件。不要读取敏感文件 |
| 审查 | 对照完成标准逐条判断；越界改动没有充分理由就列为 P1；超长 diff 给出完整文件的路径；附上 JSON 格式要求和合法示例 |
| 复审 | 不管是不是续接，都附上上一轮的 P1 和新的增量。新开会话时改用完整的审查提示词 |
| 验收修复（新增） | 失败的命令、退出码、经过扫描的输出尾部，要求修到通过 |
| 格式修正（新增） | 列出校验错误，要求按 schema 重写，不要改结论以外的内容 |
| 中断接续（新增） | 「上次执行被中断。从当前代码继续，不要推倒重来」，附上当前增量 |

## 5. 审查的独立性

- **作者集合**：本次运行中改过代码的所有模型，包括执行、修复、接手的模型，以及用 `--by` 声明的主会话。作者集合记在 `state.json` 里。
- **候选过滤**：审查者的家族不能出现在作者家族集合里。每次选审查者时都重新算一遍。
- **修复后作者变了**：如果当前审查者和新作者同家族，丢弃这个审查会话，换下一个候选，用完整的审查提示词新开会话。
- **续接审查会话的条件**：审查者没变，会话已经建立，作者集合也没有引入冲突。三者都满足才续接。
- **思考程度**：按候选自己的配置（第 8.3 节）。
- **没有候选**：交给主会话代审。主会话和作者同家族时，结论最多是「待验证（独立性不足）」。
- **过渡期**：从工作包 2 到工作包 4 之间，家族数据先用 `config.ts` 里现有的 `FAMILIES` 表；不在表里的别名一律当成家族未知，按 I2 保守处理。

补充说明：

- claude 现在给执行放开了不受限的 `Bash`（`args.ts:38`）。启用 sandbox 并设置 `allowUnsandboxedCommands: false` 之后，Bash 命令才会在沙箱内运行（二进制里有这个键，待实测）。

- `sandbox-exec` 里的路径必须先解析成真实路径。`/tmp` 实际是 `/private/tmp`，不解析的话，连工作目录内的写入都会被拦掉（已复现）。
- Apple 已经把 `sandbox-exec` 标为弃用，但本机（Darwin 25.6）可以正常使用。Linux 计划用 bubblewrap（未实测）。所在平台没有可用沙箱时，脚本不自动运行验收命令，结论为「待验证」，并列出要运行的命令，交给主会话在它自己的权限体系下运行。

- 运行目录放在 `.git/orchestrate/` 下面。执行者写不了 `.git`，所以也篡改不了运行记录。

### 6.2 哪些外壳可以担任哪些角色

- 每个外壳每一层都要有实测记录（第 12 节，由工作包 3 和 `config.sh isolation` 产生）。五层都有强制手段的外壳，才能承担执行。
- 缺任何一层，默认不能执行。用户可以在 `[safety] unsafe_exec = ["grok"]` 里显式放行，汇总会标出「X 在没有完整隔离的情况下执行」。
- pi 永远不承担执行（保持现状）。
- 只读角色（探索、方案、审查）不给 Bash 和写工具，没有写入和网络风险，但要满足第 6.4 节的读取准入。

### 6.3 授权（I6）

- `--allow <类别,...>` 的类别：`deps`、`network:<域名,...>`、`network:*`、`publish`、`deploy`、`push`、`data`、`prod-config`。默认什么都不放行。只写 `network`、既不带域名也不带 `*`，按用法错误处理，避免一不小心放开全部出站。
- 方案的 `needs_permission` 里，有任何一项的类别不在 `--allow` 里，或者类别是 `other`，就触发方案闸门（交接类型 permission）。方案里 `network` 类的需求，只要 `--allow` 里有任意一种 `network:` 写法就算已授权；实际能访问哪里，以 `--allow` 给的范围为准。
- **类别之间互不包含。** 联网授权只表示「可以访问这些地址」，不表示可以发布、推送、部署、改数据或改生产配置。这些动作要么单独出现在 `--allow` 里，要么经方案闸门由用户逐项确认。
- **联网授权怎么落到各层：**
  - `network:<域名,...>`：只在能按域名强制的层打开，并且只放行这些域名，例如 claude 沙箱的 `allowedDomains`（待实测）。不能按域名强制的层保持禁网，包括脚本跑验收用的 `sandbox-exec`（已实测不支持域名）；grok、codex 待实测。汇总写明哪些层因此没有联网。
  - `network:*`：放开全部出站，必须显式写出。汇总标出「本次 X 层不限出站」。
- **网络放开后，挡住推送和发布的就不再是物理隔离。** `.git` 只读本来就挡不住推送：实测在 `.git` 不可写的沙箱里运行 `git push`，提交照样送到了远端，失败的只是事后更新本地的 `refs/remotes/origin/*`。`npm publish`、直接调用 HTTP 接口则根本不碰 `.git`。所以：
  - 网络禁止时（默认），挡住推送、发布的是网络限制；
  - 网络放开后，剩下的约束是方案闸门、凭证隔离（第 6.6 节：拿不到 token、SSH 密钥和凭证助手，大多数需要认证的外发会失败）、下面的辅助识别和执行提示词。这些都不是完整保证，汇总要如实写明；
  - 需要硬保证的场景，不放开网络，而是让主会话在它自己的权限体系下完成那一步。
- `deps` 只放行修改依赖清单。安装通常要联网，需要另外给出 `network:<registry 域名>`。只放行 `deps` 时，汇总会提示安装可能因为禁网失败。
- 辅助识别（不承担授权边界，没识别出来不等于已经授权）：
  - 「命令」类标准里出现发布、部署、推送、`rm -rf` 等模式，并且对应类别没有授权，按缺少授权处理，触发方案闸门；
  - 增量里有依赖清单或锁文件的改动（`package.json` 的依赖字段、`bun.lock`、`package-lock.json`、`go.sum`、`Cargo.lock`、`requirements*.txt`、`pyproject.toml` 等），但没有 `deps` 授权，就打上安全标记，结论为「待验证」。

### 6.4 内容安全（I3）

规则集中在一个模块（`scripts/safety.ts`），所有入口都调用它，不在各处各写一套。

**敏感路径**（glob，默认值如下，可以用 `[safety] sensitive_extra` 追加）：

`**/.env`、`**/.env.*`（`*.example`、`*.sample`、`*.template` 除外）、`**/*.pem`、`**/*.key`、`**/*.p12`、`**/*.pfx`、`**/*.jks`、`**/*.keystore`、`**/id_rsa*`、`**/id_ed25519*`、`**/id_ecdsa*`、`**/.npmrc`、`**/.pypirc`、`**/.netrc`、`**/.git-credentials`、`**/*.kdbx`、`**/*.tfstate*`、`**/secrets/**`、`**/*secret*`、`**/*credential*`、`**/kubeconfig*`、`**/.aws/**`、`**/.ssh/**`。

这份清单不可能列全，所以还有内容扫描作为第二道防线。

**家目录里的凭证路径**（验收命令和 worker 执行的 shell 都拒绝读取；可以在 `sensitive_extra` 里用 `~/` 开头的路径追加）：`~/.ssh`、`~/.aws`、`~/.azure`、`~/.config/gcloud`、`~/.kube`、`~/.docker/config.json`、`~/.npmrc`、`~/.pypirc`、`~/.netrc`、`~/.git-credentials`、`~/.config/gh`、`~/.gnupg`、`~/.config/orchestrate`。验收命令还拒绝读取各 CLI 的配置目录（`~/.claude`、`~/.grok`、`~/.codex`、`~/.pi`）。worker 执行的 shell 能不能拒绝读取它自己那个 CLI 的目录，逐个实测。

**各入口的处理**

| 内容 | 处理 |
|---|---|
| 基线和当前快照 | 按第 7.1 节：临时索引先删掉敏感条目，候选路径在 JS 里按规则过滤，只把允许的路径交给 `git add`。敏感文件不论是否被跟踪，都不会被读取，也不在快照里 |
| 发给审查者和执行者的 diff | 由快照生成，本来就不含敏感路径，再做一遍内容扫描 |
| 敏感文件有没有被改 | 开跑时只记录 stat（大小、修改时间，范围见第 7.2 节），收尾时比较，不读内容。有变化或新增就打安全标记 |
| 探索、方案、审查回传的文本 | 扫描后才落盘、转发给下一个模型 |
| 验收命令的输出 | 截断加扫描后才落盘、转发 |
| `usage.jsonl` 里的错误信息 | 截断加扫描 |
| 汇总 | 只写路径和统计，不写内容 |

**内容扫描**：只用高置信度的模式，包括 PEM 私钥头、AWS `AKIA`/`ASIA` 密钥、GitHub `ghp_` 和 `github_pat_`、`sk-` 和 `sk-ant-` 开头的密钥、Slack `xox?-`，以及 `api_key`、`secret`、`token`、`password` 后面跟 12 位以上的值。命中时把值换成 `[已遮盖:类型]`，并打安全标记。

**worker 自己读文件（默认严格）**：

- 准入规则。一条路由要担任某个角色，它的外壳必须满足：
  - 执行：实测能拒绝读取敏感路径（仓库内的规则加上家目录凭证路径），用 claude 的 `denyRead`、grok 的 `--deny` 或沙箱等手段（均待实测）。
  - 只读角色（探索、方案、审查），满足下面任一条：
    1. 同上，实测能拒绝读取敏感路径；
    2. 实测能把读取限制在指定目录内。这时 worker 在**筛选副本**里工作：脚本把安全快照（第 7.1 节，本来就不含敏感文件）导出到运行临时目录，只把这个目录交给 worker。代价是副本里没有被 `.gitignore` 忽略的文件（如 `node_modules`），要看第三方代码时看不到。
  - 执行不用筛选副本：执行要在真实工作区里改代码、跑依赖被忽略目录的测试，导出再合并回去，复杂度和风险都高于收益。
- 不满足的路由在选择时跳过，写进汇总（I7）。一个位置的候选全部被跳过时，交给主会话。
- 例外只能逐个外壳显式放行：`[safety] unsafe_read = ["pi"]`。汇总标出「X 没有读取限制」。事后提醒挡不住已经发生的读取，所以默认不放行。
- **代价如实写出**：WP3 的隔离实测完成之前，按这条规则可能没有任何外部外壳可用，orchestrate 会把各步都交给主会话。想提前使用，就逐个外壳放行，并接受对应的风险。
- 提示词里要求不读敏感文件，只是辅助手段。

**超长 diff**：完整的、已扫描的增量写到 `diff-N.patch`，提示词里只内联上限以内的部分，并告诉审查者完整文件的路径。审查者在筛选副本里工作时，patch 文件放进副本目录；在真实工作区时，能不能读到 `.git/orchestrate/` 下的文件，还是需要用 `--add-dir` 加上运行临时目录，待实测。

### 6.5 脚本怎样运行验收命令

- 来源只有 `plan.json` 里「命令」类标准的 `commands`。删除全文兜底和工具名白名单，`rtk bun test`、`./scripts/test.sh` 都能用。
- 运行前先做授权检查（第 6.3 节）。
- 用 `sh -c` 在 `sandbox-exec` 里运行，配置按本次运行生成：
  - 可写：工作目录（真实路径）和运行临时目录；
  - 拒绝写 `.git`；
  - 默认拒绝出站网络；`--allow network:*` 时放开，只给域名时保持禁止（第 6.3 节）；
  - 拒绝读取仓库内的敏感路径和家目录凭证路径（已实测可行，正则和目录两种写法都生效）。
- 每条命令都有超时，默认 10 分钟，可以配置。超时就杀掉整个进程组，按失败处理。
- 环境变量：用 `env -i` 只传白名单，见第 6.6 节。
- 被安全规则挡住的命令单独处理。实测：拒绝读 `.env` 之后，`git status` 会报 `.env: Operation not permitted`。输出里出现对敏感路径或凭证路径的 `Operation not permitted` 时，不算代码问题，不进修复轮；结论为「待验证」，汇总列出这条命令，由用户决定。
- 记录：快照 id、命令、退出码、耗时、经过扫描的输出尾部。

### 6.6 凭证与环境变量

环境变量也是外发内容（I3）；网络放开之后，外发动作能不能带上凭证，也取决于这里（第 6.3 节）。

**脚本跑验收命令**：用 `env -i` 启动，只传下面这些：

- `PATH`（保证 `rtk`、`~/.bun/bin` 能用）、`HOME`、`USER`、`LANG` 和 `LC_*`、`TERM`；
- `TMPDIR`，指向运行临时目录；
- `GIT_CONFIG_GLOBAL=/dev/null`、`GIT_CONFIG_NOSYSTEM=1`、`GIT_TERMINAL_PROMPT=0`，让 git 找不到凭证助手（待实测）；
- `[safety] verify_env` 里声明的变量。配置里只写名字，值从当前环境取，不写进运行记录和汇总。

`HOME` 用真实家目录：go、cargo 等工具的模块缓存在家目录下，换成临时目录会让测试因为禁网下载失败。家目录里的凭证路径由沙箱拒绝读取（第 6.4 节）。实测：用 `env -i` 加白名单、在沙箱里运行，bun 和 git 都正常，可见的变量只剩传进去的几个（这次测试的 HOME 指向临时目录）。

**worker 的 CLI 进程**：同样用 `env -i` 启动，白名单同上，再加上这个外壳认证必需的变量（`[safety.cli_env]` 里按外壳声明，只写名字）。这样 `SSH_AUTH_SOCK`、`AWS_*`、`GH_TOKEN`、`NPM_TOKEN` 这类变量不会进入 worker。有两件事要分开看：

- CLI 自己认证要用的变量：必须给 CLI。各 CLI 用最小环境启动后能不能正常认证，待实测。
- CLI 执行的 shell 能看到哪些变量：取决于各个 CLI，逐个实测。如果看得到认证变量，汇总标出。这个凭证本来就交给了这个外壳，风险在于联网时被测试脚本带出去。

还有一个缺口：macOS 钥匙串里的凭证（例如 gh 的登录信息）不走环境变量，也不走普通文件，沙箱里的命令能不能取到，待实测（第 12.2 节）。

## 7. 基线与归属（I4）

### 7.1 做法（已实测）

开跑前的检查：

- 必须是 git 仓库，否则拒绝运行会改代码的流程，只读审查不受限制；
- 没有未解决的合并冲突（`git ls-files -u` 为空），否则拒绝；
- 本工作区没有其他会改代码的运行在进行（工作区锁，第 9.2 节）。

快照函数 `snapshot()`（v2.1 修订，已实测）。全程使用本次运行专用的临时索引文件（`GIT_INDEX_FILE`）：

1. 临时索引从**用户暂存区的副本**开始：只复制文件，不改原文件；没有暂存区文件时从空开始。这样既保留了用户已暂存的状态，也能沿用 git 的文件状态缓存，只重新读取改过的文件。
2. 从临时索引里强制移除所有匹配敏感规则的条目（`git update-index --force-remove -z --stdin`）。不用 `git rm --cached`，避免暂存内容与 HEAD、工作区都不同的时候拒绝移除；不为比较而读取敏感内容。
3. 候选路径 = 临时索引里的条目 + 未跟踪且未被忽略的文件（`git ls-files -o --exclude-standard`），去掉敏感路径，对其余路径运行 `git add -A`。删除、文件模式变化、符号链接都会如实反映。
4. 对临时索引运行 `git write-tree`，得到快照 id。

实施补充（2026-10-27）：只对临时索引清除 `assume-unchanged`，避免漏掉工作区改动。当前对 sparse checkout、skip-worktree、未解决冲突及 submodule 显式拒绝，不盲目展开或删除。Git clean/smudge/process filter、fsmonitor 与 hooks 在快照和导出操作中禁用，避免拍照时执行仓库配置的命令。

路径列表一律用 NUL 分隔（`--pathspec-from-file` 加 `--pathspec-file-nul`），并设 `GIT_LITERAL_PATHSPECS=1`，避免文件名里的特殊字符被当成通配符（已实测可用）。

**安全 HEAD 树** `safe_head()`：临时索引 `git read-tree HEAD`（还没有提交过的仓库用空树），删掉敏感条目，再 `write-tree`。「开跑前已有修改」和只读审查的「HEAD → 当前」都拿它来比较。所有比较都在安全树之间进行，所以敏感路径不会以任何形式（包括「被删除」）出现在 diff 里。

**不碰用户暂存区**：

- 「真实暂存区的树」也对副本计算，不直接对用户暂存区运行 `git write-tree`。实测：直接运行会改写用户的暂存区文件（缓存树扩展），文件指纹从 `6d05d03ada6c` 变成了 `9b0770868e06`。
- orchestrator 对用户仓库运行 `git status` 这类命令时，一律设 `GIT_OPTIONAL_LOCKS=0`，避免顺手刷新暂存区（依据 git 文档对这个变量的说明；实测设了之后指纹不变）。

未跟踪文件的内容会作为 blob 存进本地对象库，不发给任何人，没有引用的对象以后由 git gc 清理。

开跑时记录：HEAD、真实暂存区的树（对副本计算）、基线快照、安全 HEAD 树、敏感文件的 stat（范围见第 7.2 节）、开跑前就有修改的路径（`git diff --name-only <安全 HEAD> <基线>`）。

2026-10-26 在临时仓库里实测：

- v2 的算法（`read-tree HEAD` 之后只 add 安全路径）有两个漏洞，都已复现：已被 HEAD 跟踪的 `.env` 留在了快照里；用户 `git rm` 掉的文件也留在了快照里。
- 修订后的算法：
  - 快照里没有 `.env`，不论它是否被跟踪；用户 `git rm` 的文件、在工作区里删掉的文件，都不在快照里；
  - 文件模式（`100755`）和符号链接（`120000`，只记录指向的路径，不读目标文件）都如实记录；
  - 「安全 HEAD → 基线」列出了开跑前的全部修改（修改、删除、新增、模式变化），其中没有 `.env`；
  - 之后同时改 `.env` 和普通文件，增量里只有普通文件；
  - 多次快照前后，用户暂存区文件的指纹不变；
  - 还没有提交过的仓库：快照正常，安全 HEAD 是空树。
- v2 的第一次实测还验证过：已暂存的改动、开跑前就存在后来又被改的未跟踪文件都能进增量。修订后的算法同样按工作区内容生成，WP1 的测试会再覆盖一遍。

### 7.2 用途

- 每个执行或修复步骤结束后都拍一次快照。增量 = `git diff <基线> <当前>`。
- 审查的输入：增量（经过扫描）、和用户原有修改重叠的文件、越界文件（增量里不匹配 `allowed_paths` 的路径）。
- 汇总里的「改动」只统计增量。
- 收尾检查：
  - 真实暂存区的树变了，打安全标记；
  - HEAD 变了，打安全标记；
  - 敏感文件的 stat 变了，或者出现了新的敏感文件，打安全标记。
- 敏感文件 stat 的记录范围：暂存区里的、未跟踪的，以及被忽略的文件中匹配规则的。`.env` 通常就是被忽略的，不覆盖这一类，最常见的敏感文件被改了也发现不了。被忽略的文件用 `git ls-files -o -i --exclude-standard --directory` 列出，整目录被忽略的（如 `node_modules/`）折叠成一行、不展开。实测：根目录下被忽略的 `.env` 能列出来。整目录被忽略的目录里的敏感文件不追踪，是已知限制。全程只取 stat，不读内容。
- 被 `.gitignore` 忽略的文件不在快照里，执行者对它们的改动（例如构建产物）不在审查范围内。这是已知限制。

### 7.3 git worktree 和非 git 目录

- 运行目录和锁都放在 `git rev-parse --git-dir` 指向的目录里，每个 worktree 各自独立。
- 非 git 目录：拒绝会改代码的运行。只读审查的记录放在 `${XDG_STATE_HOME:-~/.local/state}/orchestrate/` 下面，不写进项目目录。

## 8. 位置、能力与本机适配（物尽其用）

### 8.1 三层

| 层 | 归谁 | 内容 |
|---|---|---|
| 能力目录 | skill，`references/catalog.toml` | 能力名、家族、匹配本机 ID 的正则、各外壳上默认支持的思考程度 |
| 位置 | 用户，`routing.toml` | 每个位置用哪些能力、按什么顺序、各用什么思考程度 |
| 路由 | 用户本机，`models.conf`，由 init 生成 | 能力名 → 外壳 + 本机真实 ID。同一能力可以有多条路由 |

能力名是 skill 内部统一使用的代称，和任何 CLI 里的显示名、ID 都没有关系。同一个模型，在不同机器、不同外壳、不同网关上 ID 都可能不一样。例如本机的 grok 上，Grok 4.7 Fast 既有原生的 `grok-4.7-build-fast`，也有网关的 `magpie/grok/grok-4.7-build-fast`。

### 8.2 能力目录（示例已解析通过）

~~~toml
["opus-5.5"]
family = "anthropic"
match = ['claude-opus-5[.-]5']

["gpt-6.1-sol"]
family = "openai"
match = ['gpt-6[.-]1-sol']

["grok-4.7-fast"]
family = "xai"
match = ['grok-4[.-]7-(build-)?fast']
efforts.grok = ["low", "medium", "high", "xhigh"]

["glm-5.3-flash"]
family = "zhipu"
match = ['glm-5[.-]3-flash']
efforts.grok = ["low", "high", "max"]
efforts.pi = ["off", "minimal", "low", "medium", "high", "xhigh", "max"]
~~~

- 名字里带点的表名必须加引号。不加引号时，`Bun.TOML.parse` 直接报错（已复现）。
- 实测的匹配结果：
  - `gpt-6[.-]1-sol` 能匹配 `magpie/group/auto-gpt-6-1-sol` 和 `magpie/copilot/gpt-6.1-sol`，不匹配 `gpt-6-sol`；
  - `grok-4[.-]7-(build-)?fast` 能匹配原生和网关两种写法，不匹配 `grok-4.7`。
- `efforts.<外壳>` 是**支持的档位集合**，不是要用的档位。要用的档位在 `routing.toml` 里配。

### 8.3 位置配置 `routing.toml`（示例已解析通过）

~~~toml
[positions.explore]
chain = [{ model = "haiku-5.5", effort = "low" }, { model = "glm-5.3-flash", effort = "low" }]
timeout_min = 5

[positions.plan]
chain = [{ model = "opus-5.5", effort = "medium" }, { model = "gpt-6.1-sol", effort = "high" }]
timeout_min = 10

[positions.review]
chain = [
  { model = "gpt-6.1-sol", effort = "xhigh" },
  { model = "grok-4.7", effort = "high" },
  { model = "opus-5.5", effort = "medium" },
]
max_rounds = 2
timeout_min = 15

[positions.exec]
effort = "high"
default_pool = "standard"
timeout_min = 30

[positions.exec.pools]
mechanical = ["glm-5.3-flash", "deepseek-v4.1-flash", "haiku-5.5"]
standard = ["grok-4.7", "sonnet-5.5"]
hard = [{ model = "gpt-6.1-sol", effort = "high" }, { model = "opus-5.5", effort = "high" }]

[safety]
sensitive_extra = ["**/*.sqlite", "exports/**"]
# 下面两项默认为空：没有实测读取限制或完整隔离的外壳，不担任对应角色
unsafe_read = []
unsafe_exec = []
# 验收命令在白名单之外还需要的环境变量名（只写名字）
verify_env = []

[safety.cli_env]
# 各外壳认证必需的环境变量名，实测后填写
pi = []
~~~

- 每个候选都带自己的思考程度。opus 顶替 gpt 做审查时用 medium，由配置格式本身表达，不再靠单独的 `fallback_effort`。
- 执行池的条目可以是字符串（用 `positions.exec.effort`），也可以是 `{ model, effort }`。两种混在同一个数组里也能解析（已实测）。
- 不再使用的项：
  - `[triage]`：外派门槛留在 SKILL.md，按对比实测调整；
  - `fallback`、`fallback_effort`：已经被候选链取代；
  - v2 示例里的 `strict_read`、`network`：读取改为按外壳放行的 `unsafe_read`；网络只能用 `--allow` 按次放行，不在配置里设默认值。
- `[safety]` 里的列表都只写名字或路径，不写变量的值。v2.1 的 `[safety]` 段已解析通过。
- 解析改用 `Bun.TOML.parse`（内置，不引入新依赖），替换 `config.ts:101-198` 的手写解析器，然后再做结构校验。

### 8.4 本机路由 `models.conf`

格式：

~~~
# <能力名> <provider> <本机 ID> [key=value ...]
# key：family=  efforts=逗号分隔  price=输入,输出,缓存读,缓存写（美元/百万 token，可以留空位，如 price=5,25,,）
opus-5.5       claude  claude-opus-5-5                price=5,25,0.5,6.25
gpt-6.1-sol    grok    magpie/group/auto-gpt-6-1-sol  # 待实测能否调用
grok-4.7-fast  grok    grok-4.7-build-fast            efforts=low,medium,high,xhigh
my-model       pi      vendor/foo                     family=acme
~~~

解析规则：

- 未知的 key、同一行里重复的 key，都报错。
- 旧格式（第 4–7 列直接写价格数字）仍然接受，`check` 会提示迁移。
- 家族取值顺序：本行的 `family` → 能力目录 → 都没有就在加载时报错。
- 支持的档位取值顺序：本行的 `efforts` → 能力目录里这个外壳的值 → 都没有就不折算，交给 CLI 自己拒绝。
- 要用的档位来自 `routing.toml`。不在支持集合里时，取最近的一档，距离相同取更高的一档，并记进账本。

### 8.5 加载校验（运行开始前，0 token）

以下情况直接报错停下：

- `routing.toml` 引用了 `models.conf` 里没有的能力；
- 某个能力没有家族；
- 思考程度的取值不认识；
- 执行池为空，或者 `default_pool` 指向不存在的池；
- 方案或审查的候选链为空；
- 某个执行池里只有 pi 的路由；
- provider 名字不认识；
- `--exec` 指定的能力不存在（现状是被当成「没有可用模型」交给主会话）。

外壳没安装、没登录只给警告，由预检决定实际阵容。

配置来源分四种情况：

| 情况 | 处理 |
|---|---|
| 用户目录里两个文件都在 | 使用用户配置 |
| 用户目录里只有其中一个 | 报错，提示运行 `config.sh init` 迁移。本机现在就是这种情况：有旧的 `models.conf`，没有 `routing.toml` |
| 用户目录里都没有 | 使用示例配置，汇总里注明 |
| 带了 `--sample` | 使用示例配置 |

### 8.6 init 适配（分两步，不需要交互）

两步都不需要在终端里交互，方便主会话代为执行和转述。

1. **`config.sh init --propose`**
   - 探测已安装、已登录的 CLI 有哪些模型：grok 用 `grok models`，pi 用 `pi --list-models`，codex 用 `codex debug models`。claude 没有列出模型的命令，只用能力目录里已知的 ID。
   - 用能力目录的正则去匹配，写出 `models.conf.proposed`、`routing.toml.proposed`，并打印一张可读的表：每个能力有哪些候选路由（原生、网关、group 等），以及哪些本机模型没匹配上。
   - 不改动现有文件。
2. 主会话把这张表给用户看，由用户选路由、排优先级。
3. **`config.sh init --apply`**：现有文件先带时间戳备份，再写入，然后自动运行 `check`。
   - 迁移旧配置：保留原来的行，位置价格列转成 `price=`；`routing.md` 不再读取，打印提示。

**档位探测，尽量 0 token**：重设计方案第 16.4 节记录，grok 遇到非法档位时，会在发出请求**之前**拒绝，并列出允许的档位。`config.sh efforts` 可以对每条 grok 路由传一个非法档位，从报错里读出允许的列表。这样做是否真的不发请求，要逐条路由实测。

**`config.sh probe [路由]`**：会花 token。只在用户明确同意后运行，先显示要调用几次和预估金额。结果记录为：成功或失败、日期、用的档位、CLI 版本。

一次探测成功，只能证明「这条路由、用这组参数、在当时能回答」。证明不了其他档位能用，证明不了它能胜任实际任务，也证明不了隔离有效。

**`config.sh isolation <provider>`**：发一次执行角色的调用，让它分别尝试写工作目录以外、写 `.git`、联网，用来验证隔离。会花 token，要用户同意。结果写进外壳准入记录（第 6.2 节）。

### 8.7 默认位置（起点，按对比实测调整）

| 位置 | 默认（按顺序） | 理由 |
|---|---|---|
| 方案 | opus-5.5 · medium → gpt-6.1-sol · high | 方案质量决定后面所有阶段 |
| 审查 | gpt-6.1-sol · xhigh → grok-4.7 · high → opus-5.5 · medium | 审查能力强；按家族排开，保证总有一个异家族的候选 |
| 执行 · hard | gpt-6.1-sol · high → opus-5.5 · high | 疑难逻辑需要顶级推理，备选不降档 |
| 执行 · standard | grok-4.7 → sonnet-5.5 | 常规功能，看性价比 |
| 执行 · mechanical | glm-5.3-flash → deepseek-v4.1-flash → haiku-5.5 | 机械改动，选最便宜的 |
| 探索 | haiku-5.5 · low → glm-5.3-flash · low | 只读、轮次多、需要的思考少 |
| grok-4.7-fast | 暂不路由。能力目录里保留，init 可以先把它映射好 | 等对比实测再决定放在哪 |

gpt-6.1-sol 在本机能不能用，取决于选哪条路由。之前回 400 的是 `magpie/copilot/gpt-6.1-sol`；本机 grok 上还有 `magpie/group/auto-gpt-6-1-sol`，待实测。

### 8.8 替换规则

- 只在这个位置的候选链里替换，下一个候选用它自己的思考程度。
- 执行模型失败时，换同一个池里的下一个，新开会话，用接手提示词（附上方案、当前增量、进度和原因）。
- 池里的候选都用完了，交给主会话做执行，不跨池升级（和「不做升级梯子」一致）。
- 每次替换和跳过都写进汇总。

## 9. 可靠性与调度

### 9.1 状态和检查点

`state.json` 记录：

- 版本、运行 id；
- `status`：running、waiting、done、interrupted；
- `step`：explore、plan、exec、verify、review、fix、check、finalize；
- 修复轮次、作者集合、各角色的会话；
- 快照：基线、最后验收、最后审查、当前；
- `workers`：正在运行的子进程（CLI 和验收命令），每个记 pid、进程组 id、启动时间、命令名、角色；
- 待处理的交接、`allow`、`exec_pin`、预算和调用次数、时长上限，以及各时间戳。

每个步骤开始和结束时，都以「先写临时文件，再改名」的方式原子写入。

### 9.2 互斥

- **运行锁** `<运行目录>/lock`：内容是 pid、主机名、启动时间，用独占方式创建。
  - continue 时，如果锁的主机是本机、pid 还活着，拒绝并提示「运行仍在进行」；
  - pid 已经不在了，不直接接管，先做下面的 worker 存活检查；
  - 锁的主机不是本机，拒绝，并给出手动解锁的说明。
- **工作区锁** `<git-dir>/orchestrate/worktree.lock`：会改代码的运行必须持有。同一个工作区的第二个会改代码的运行会被拒绝。只读审查不加这把锁。
- **信号**：收到 SIGINT 或 SIGTERM 时，杀掉子进程所在的进程组（子进程放进单独的进程组启动），把状态写成 interrupted，释放锁。
- **worker 存活检查**。主进程被 SIGKILL 或者异常退出时，上面的清理不会执行，worker 也不会跟着退出。实测：父进程被 SIGKILL 后，用 `Bun.spawn` 启动的子进程和用 `detached` 启动的子进程都还活着；`detached` 的子进程有自己的进程组 id。所以：
  - 每个 worker（CLI 进程和验收命令）都用 `node:child_process` 的 `detached: true` 启动，拿到独立的进程组；启动后立即把身份写进 `state.json` 的 `workers`；
  - 恢复前逐个检查：进程组还在，并且组长的 pid、启动时间（`ps -o lstart=`）、命令名都和记录一致，或者组长已经退出但组里还有进程，都视为旧 worker 仍在运行。这时拒绝推进，提示运行 `orch.ts stop`；
  - 进程组已经不存在，或者 pid 已被别的进程复用（启动时间对不上），视为已停止；
  - 查不了（`ps` 失败、权限不足、记录缺失），拒绝推进。
- **`orch.ts stop --run <目录>`**：核对身份后，向记录里的进程组发 SIGTERM，等一段时间仍不退出再发 SIGKILL，然后把状态写成 interrupted。只处理记录在案、身份吻合的进程组。由用户或主会话显式运行，主会话运行前先告诉用户。
- worker 用 `setsid` 之类的方式脱离进程组的后代进程追踪不到，列为剩余风险（第 13.3 节）。

### 9.3 恢复语义

所有恢复都要先通过第 9.2 节的 worker 存活检查。

| 中断时在做什么 | 恢复做法 |
|---|---|
| 探索、方案、审查 | 重跑。会话已经建立就续接，否则新开 |
| 执行、修复 | 不重放原来的提示词。先拍当前快照；会话已经建立，就续接并发中断接续提示词，附上当前增量；否则从同一个池里新开会话接手 |
| 验收 | 重跑 |
| 各类交接 | 等主会话 continue |

### 9.4 调用、重试与替换

- **会话算「已建立」**的唯一条件：之前有一次成功调用记录了这个会话 id。只有已建立的会话才续接（修 `flow.ts:380-388`）。
- **临时错误**（429、5xx、网络、超时）：等一会儿重试一次。会话已建立就续接，没建立就换一个新 id。
- **思考档位被拒绝**：按报错里给出的允许列表调整，重试规则同上。
- **确定性错误**：换下一个候选。
- **不可用缓存**：`~/.cache/orchestrate/unavailable.json`，按「外壳 × 模型 ID」记录。
  - 只缓存明确的「模型不支持」「model_not_found」「无权使用该模型」这几类，默认 24 小时过期；
  - 登录类错误不缓存，由预检处理；临时错误也不缓存；
  - 汇总里显示跳过了哪些、原因、多久前确认的；
  - `config.sh cache clear` 可以清空；
  - 文件损坏时忽略并重建。

## 10. 账本与成本控制（I8）

### 10.1 每次调用记录的内容

`usage.jsonl` 每行一次调用，包含：

- 运行、位置、能力、外壳、实际计费的模型 ID；
- 思考程度（请求的和实际的）、会话、是否续接、耗时；
- token：新输入、缓存读、缓存写、输出、思考；
- 金额：数值和来源（`cli`、`price`、`unknown`、`not_sent`）；
- 结果（`ok`、`error`、`timeout`）和错误类别。

**失败的调用怎么记**（I8）：

- 失败时也解析 stdout 和 stderr。claude 的 `is_error` 结果、grok 的 error 行、pi 的 `stopReason: error` 消息都可能带着用量或报价，拿到就记。现状是 `cli-provider.ts:42` 遇到非零退出码直接抛错，用量被丢掉（Q35）。
- 解析不到：token 和金额都记为未知，不写 0。
- 超时被杀：记为未知。
- 只有能证明请求没有发出、或者确定没有计费时，才记 0，来源写 `not_sent`。例如 CLI 不存在、参数在本地就被拒绝、预检失败。grok 在发出请求前拒绝非法档位的情况，要先实测确认真的没发请求（第 12.2 节）。
- 因为不可用缓存而跳过的路由，根本没有发生调用，不进账本，只写进汇总的「跳过」。

### 10.2 要修正的地方

### 10.3 省钱的机制

1. 分流：小活由主会话自己做（SKILL.md）。
2. 探索只做一次，笔记直接交给方案阶段，方案阶段不重新探索。
3. 先验收再审查，跑不通的代码不浪费一次审查。
4. 修复续接原来的执行会话，复审续接原来的审查会话，能吃到缓存。
5. 不可用缓存，跳过注定失败的调用。
6. 按候选配置思考程度，避免 opus 顶替审查时用 xhigh。
7. 只读审查默认只派一个模型。
8. 超长 diff 写进文件，不在提示词里反复内联。
9. 默认不做付费探测。

**预算与上限**（工作包 7）。三个参数分别管三件事：

- `--budget <美元>`：只管**已知金额**（CLI 报价，加上按价格估算的部分）。每次发起调用前检查，已经达到上限就不再发起新调用，交给主会话（交接类型 budget）。对已知金额来说，最多超出一次调用的花费；单次调用本身会花多少，没有上限。
- `--max-calls <次数>`：本次运行的模型调用总数，失败和重试也算在内。用来约束金额未知的调用。
- `--max-minutes <分钟>`：本次运行的总时长。
- 任何一个达到上限都会停下，交接类型都是 budget。
- 带了 `--budget`，而预检发现本次阵容里有路由既没有 CLI 报价、也没有价格列时，必须同时给出 `--max-calls` 或 `--max-minutes`，否则按用法错误处理，报错里列出这些路由。汇总写明「预算不覆盖 N 次未报价的调用」。
- 有金额未知的调用时，不承诺实际支出最多超出多少。

**`orch.ts report`**：汇总所有运行的 `usage.jsonl`，按位置和能力统计调用次数、失败率、平均金额、修复轮次，用来调整池子顺序和思考程度。

### 13.2 每个机制在五种异常下的行为

| 机制 | 内容为空 | 矛盾或重复 | 中途被打断 | 执行失败 |
|---|---|---|---|---|
| 方案契约 | 没有标准就无效 | 键重复、`id` 重复都无效 | 重跑方案 | 换下一个候选 → 交给主会话 |
| 审查契约 | 空数组表示明确没有问题，缺字段无效 | 键重复无效；快照 id 不一致无效 | 重跑审查 | 换下一个候选 → 交给主会话 |
| 验收 | 没有命令类标准就跳过，走核验交接 | 不适用 | 重跑 | 命令超时算失败；没有沙箱时结论为「待验证」 |
| 基线 | 没有提交过的仓库，安全 HEAD 是空树 | 有合并冲突就拒绝；已跟踪的敏感文件从临时索引里删掉 | 基线 id 已经记在 `state.json` 里 | 拍快照失败时，在调用任何模型之前停下 |
| 独立性 | 没有候选就交接 | 修复后作者变了，重新选 | 作者集合已持久化 | 主会话代审时，同家族就标「待验证」 |
| 方案闸门 | 不适用 | 类别是 `other` 一律闸门 | 处于等待状态 | 用户拒绝，结束并保留方案 |
| 锁 | 不适用 | 跨主机的锁拒绝，给出手动解锁说明 | 主进程不在时先查 worker：还在运行、或者查不了，都拒绝推进；确认已停止才接管 | `stop` 只处理身份吻合的进程组 |
| 配置 | 只有一个文件就报错 | 未知 key、重复 key 报错 | 不适用 | 加载失败，0 token 停下 |
| 不可用缓存 | 没有文件就新建 | 文件损坏就重建 | 不适用 | 误判的影响以 24 小时为限；可以手动清空 |
| 账本 | 未知金额 → 合计显示「≥」 | claude 累计值换算成差值（待实测） | 每次调用都即时落盘 | 失败的调用也记录：能解析出用量就记，否则记为未知；只有能证明没发出请求时才记 0 |
| 网络授权 | 只写 `network`、不带范围 → 用法错误 | 只给了域名，但某层不能按域名限制 → 这一层保持禁网 | 不适用 | 不适用 |
| 读取准入 | 某个位置的候选全部不满足 → 交给主会话 | 不适用 | 不适用 | 准入实测失败 → 这个外壳按「没有读取限制」处理 |
| 预算 | 有未报价的路由 → 必须同时给出次数或时长上限 | 不适用 | 已用金额、调用次数、时长都在账本和 `state.json` 里，恢复后接着算 | 任何一个上限达到 → 交接 |

### 13.3 剩余风险（如实声明）

1. 用户用 `unsafe_read` 放行的外壳，worker 有可能主动读取敏感文件，内容会随它的模型请求发出去。默认不放行。
2. Apple 已经把 `sandbox-exec` 标为弃用，将来的系统版本可能不再提供。届时验收会退回「待验证」，不会悄悄在没有沙箱的情况下运行。
3. 内容扫描只认高置信度的模式，覆盖不全。敏感路径规则也列不全。
4. 被 `.gitignore` 忽略的文件改动不在审查范围内；整目录被忽略的目录里的敏感文件，改动检测不到。
5. CLI 认证必需的变量可能被它执行的 shell 看到（逐个实测，汇总里标出）；macOS 钥匙串里的凭证能不能被沙箱里的命令取到，待实测。
6. 网络被放开后，推送、发布、调用生产接口都没有物理隔离，只靠方案闸门、凭证隔离和辅助识别。
7. worker 用 `setsid` 之类的方式脱离进程组的后代进程，存活检查和 `stop` 都追踪不到。
8. 预算只管已知金额；金额未知的调用只受次数和时长上限约束。
9. 运行期间用户手动改了文件，会被计入本次增量。SKILL.md 会提醒。
10. 所有模型都会看到它角色需要的代码。这是外派本身固有的，和主会话自己读代码没有区别。

### 15.4 运行模式开关（2026-10-27）

为保留原先“主控模型一路完成”的低开销路径，技能层增加任务级模式选择：

- `simple`：不启动 `orch.ts`、不调用外部 worker、不读取动态路由；由当前主控模型完成理解、方案、实现、验收、自审和汇报。
- `dynamic`：沿用本方案的多模型动态路由流程；必须由用户明确开启或设置 `ORCHESTRATE_MODE=dynamic`，不作为默认路径。

优先级为用户本次明确指定 > `ORCHESTRATE_MODE`（仅允许 `simple` / `dynamic`）> 默认 `simple`。模式在首次模型调用或代码修改前确定，运行中不切换；简单模式的测试和自审是主控证据，不宣称具备独立 reviewer 证据。
